# 利用安全整改方案：最小化验证 + 理论扩展 + 人工审批执行

> 背景：ARTEX 在验证漏洞时会真实触发利用，payload 由模型现场生成，存在破坏目标业务可用性 / 系统可用性的风险（写文件、删除、批量导出、长时间 sleep、命令执行回连等）。本方案把「验证」和「扩大影响」拆成两件事：验证只做**最小可行证明**，扩大影响**只产出理论步骤**，真正执行必须由人在漏洞详情页审核批准后、在受控执行器里跑。

## 0. 设计目标与不变量

1. **能证明即可**：任何漏洞的"确认"只要求一条最小、可复现、低影响的证据；不要求"打穿"。
2. **越权动作零默认**：分级超过任务上限的动作，默认既不执行也不排队等待，而是**拒绝并引导产出提案**（阻塞式审批会让 worker 卡死超时，探索阶段没人值守）。
3. **人能看见、能拦住、能追溯**：每条提案在漏洞详情页可见，批准绑定到具体动作而不是笼统授权；谁批的、跑了什么、结果如何全部留痕。
4. **不靠提示词**：提示词只是引导；真正的边界在 `guard`（工具调用闸门）+ 审批凭证 + 受控执行器。
5. **项目隔离**：新表全部带 `project_id`，与既有分层一致（项目 ⊃ 企业 ⊃ 任务）。

一条必须说清的现实：worker 手上只要有 `Bash` + 出网代理，就**无法从能力上根除**危险动作。所以方案的重心不是"限制工具"，而是"所有高影响动作默认 deny，放行必须携带一条绑定到具体动作指纹的、由人签发的凭证"。这是本方案唯一能给出硬保证的机制。

## 1. 影响等级模型（按效果分级，不按 payload）

| 等级 | 定义 | 举例 | 默认 |
|---|---|---|---|
| **L0 只读证明** | 不改变目标状态，不导出真实数据 | 反射型 XSS 弹窗；SQLi 用 `' AND 1=2` / `' AND 1=1` 布尔差异；报错回显；时间盲注 ≤1s；带外到自有 collaborator；SSRF 读取自身可控地址 | 允许（自动） |
| **L1 自控对象变更** | 只改自己创建的、可撤销的对象 | 在自己注册的账号里改昵称证明越权；上传自己命名的测试文件后删除 | 允许（自动） |
| **L2 受限读取** | 读到 1 条非本人数据 / 1 个越权接口 | 越权读取 1 条他人订单；IDOR 取回 1 条记录 | 允许到 1 条，超量必须审批 |
| **L3 高影响** | 写目标文件、命令执行、持久化、提权、横向、删除、批量导出、DoS/sleep、反弹 shell | webshell、`INTO OUTFILE`、dump 用户表、`pg_sleep(30)`、并发压测 | 必须审批 |
| **L4 禁止** | 大规模导出、加密勒索、向真实第三方投递、供应链改动 | 全库 dump、批量删账号 | 永远禁止（审批也不放行） |

分级判定顺序：**动作效果 > 声明的意图**。模型说"我只读一条"但命令是 `SELECT * FROM users`，按 L3 处理。

任务级默认上限 **L1**（可配置到 L0/L2；不允许把默认值配到 L3）。上限存在 `task_constraints` 上，随每轮 prompt 注入，同时被闸门读取——**注入只影响提示，闸门才是判决**。

## 2. 三层结构

```
┌─ 引导层（软）  worker/main prompt + task_constraints + 工具描述
├─ 闸门层（硬）  guard.PreToolUse → 拦截规则 → 审批凭证 → allow/deny
└─ 执行层（受控） 审批通过后由受控执行器跑：动作指纹白名单 + 时间窗 + 速率 + 熔断
```

三层都要做，因为各自防的东西不同：引导层决定"模型通常不越界"，闸门层决定"越界了也执行不了"，执行层决定"批准了也只跑批准的那一下"。

## 3. 引导层：最小化利用原则

### 3.1 worker / mainagent 提示词

在 `agent/worker.go` 的 `workerDefaultTmpl` 与 `agent/mainagent`/`pentest` 提示词中加一节（同时作为 code-owned 尾部保证，避免被 DB 覆盖版本丢掉）：

- **验证只做最小可行证明**：先想"哪一条最低影响的证据足以证明这个漏洞存在"，做完就停，不继续加深。
- **禁止把"加深利用"当验证**：命令执行只跑 `id`/`whoami`/`hostname`，不读业务数据、不留文件、不建账号；SQLi 用布尔/时间（≤1s）证明，不 dump 表、不用 `INTO OUTFILE`、不做 `pg_sleep` 长延时；文件读取只读系统标识文件，不读配置里的凭据。
- **不制造副作用**：不写目标磁盘、不改配置、不重启服务、不清日志、不删数据；必须写时只用自己命名的临时对象并在同一次操作里删除。
- **不做可用性实验**：不并发压测、不放大请求体、不制造大量错误日志。
- **要扩大影响时，产出提案而不是执行**：调用 `propose_escalation`，写清目标、步骤、预期影响、影响面、停止条件、回滚方式、更低的替代验证；然后回到正常流程。
- **拿不准就降级**：判断不了某动作会不会影响业务时，按更高一级处理，写提案。

### 3.2 每类漏洞的"够用证据"清单（写进提示词，也可进知识库）

| 漏洞类 | 允许的最小证明 | 明确禁止 |
|---|---|---|
| SQL 注入 | 布尔差异（真/假各一次）、报错回显、≤1s 时间盲注 | dump 表、`INTO OUTFILE`、`DROP/UPDATE/INSERT`、长 sleep |
| 命令执行 | `id` / `whoami` / `hostname` | 读业务数据、写文件、反弹 shell、提权 |
| 任意文件读取 | `/etc/hostname` 或同类的非敏感标识文件 | 读 `/etc/shadow`、私钥、数据库配置、业务数据 |
| 文件上传 | 上传无害内容（如自命名的 txt）+ 能访问到 | webshell、覆盖既有文件、写到 web 根可执行位置 |
| SSRF | 请求到自有 collaborator 或目标自身的非敏感内网地址 | 探测内网资产清单、读云元数据并落盘、访问第三方真实站点 |
| 越权 / IDOR | 取回 1 条、可比对的最小对象 | 遍历、批量拉取 |
| XSS | 弹窗/`alert` 或自有回连 | 打管理员 cookie、持久化、蠕虫 |
| 反序列化 / RCE 链 | 无害回显命令（`id`） | 落地内存马、写文件、横向 |

这份清单是"最小化"的可执行定义，比一句"请最小化"有用得多。

### 3.3 约束（`task_constraints`）

- 现有 `kind in ('allow','deny')` 的文本约束保留（自然语言红线）。
- 新增结构化字段：`impact_cap`（L0/L1/L2）落在任务/项目级，注入时单独成段，闸门直接读。
- 建议在项目设置里给"默认影响上限"，任务创建时可覆盖，且**只能往下调**（默认 L1，任务可设 L0）。

## 4. 闸门层：默认 deny + 审批凭证

### 4.1 新增内置拦截规则组「[内置] 利用扩展 / 高影响动作」

沿用现有 `intercept_rules`（`match_target=tool_input`、`match_type=regex`、`action`、`priority`、`message`），按项目播种（`db/db.go` 的 `seedInterceptRules`）。方向：

| 规则 | 覆盖 | action | 优先级 |
|---|---|---|---|
| 数据库写入/导出 | `INTO OUTFILE`/`DUMPFILE`、`UPDATE`/`INSERT`/`DELETE` 作用于非自建表、`COPY ... TO`、`mysqldump`/`pg_dump` | deny（指引提案） | 85 |
| 目标落地文件 | `curl -o/-O` 到目标侧、`> /var/www`、`wget -P`、`scp`/`sftp` 上传、`base64 -d > *.php/.jsp` | deny（指引提案） | 85 |
| 命令执行加深 | `bash -i`、`nc -e`、`/dev/tcp`、`python -c` 反弹、`socat`、`chmod +x` 后执行、`curl \| sh` | deny（指引提案） | 85 |
| 持久化 | `crontab`、`systemctl enable`、`/etc/rc.local`、注册表 Run、计划任务、`authorized_keys` | deny | 90 |
| 提权/横向 | `sudo`、`su -`、`mimikatz`、`psexec`、`wmiexec`、`ssh` 到非目标主机、`impacket` | deny | 90 |
| 数据库批量导出 | `--dump`/`dumpDatabase`、`COPY ... TO`、`SELECT ... INTO OUTFILE`、带 `UNION SELECT` 拉全表 | deny（指引提案） | 80 |
| 破坏类（已有） | `rm -rf`、`DROP`、`TRUNCATE`、`FLUSHALL`、`DELETE` 请求等 | 保留 deny | 100 |

**关键点**：`action` 用现有 `deny`，但 `message` 必须写明"如需执行，请在漏洞详情 → 利用验证 提交扩展提案并获批"，把拒绝变成可继续的下一步，而不是死路。

不引入阻塞式 `ask`：探索阶段无人值守，`HandleAsk` 会等满超时才返回，既卡任务也拿不到有效审批。**审批一律异步发生在漏洞详情页**。

#### 规则要窄：宁可漏，不可误伤探测能力

上面这组规则只覆盖**效果明确是"写/落地/持久化/提权/横向/批量导出"**的动作，刻意不收：

- 普通 `SELECT`、`SELECT *`、`LIMIT` 大小——布尔/报错型注入天天要跑查询，按语句形状拦会直接废掉 SQLi 探测；
- `sleep(`/`pg_sleep(` 本身——时间盲注是标准手段，只拦**长延时**（≥5s）且只作为提案提示，不做硬 deny；
- 并发数与请求体积——不写进正则（正则数不清并发），改成**静态配置的上限**（默认关或很宽松），见 §6.1；
- 任何"看起来像攻击"的 payload 形状——payload 长什么样本来就是要探的东西。

一条判断标准：**规则命中后，如果人会认为"这本来就该先问我"，才写进规则**；如果人多半会说"这不就是正常测试吗"，就不要写。

### 4.2 审批凭证（capability）

现有 `intercept_pending` 是"一次调用一次审批"，不适合"批准一组步骤"。新增：

```sql
CREATE TABLE IF NOT EXISTS exploit_approvals (
    id            BIGSERIAL PRIMARY KEY,
    project_id    BIGINT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    escalation_id BIGINT NOT NULL REFERENCES finding_escalations(id) ON DELETE CASCADE,
    finding_id    BIGINT NOT NULL,
    fingerprint   TEXT NOT NULL,          -- 规范化动作指纹
    allowed_hosts TEXT[] NOT NULL DEFAULT '{}',
    max_level     INT  NOT NULL,
    status        TEXT NOT NULL DEFAULT 'active'
                  CHECK (status IN ('active','consumed','expired','revoked')),
    approved_by   TEXT NOT NULL,
    approval_note TEXT NOT NULL DEFAULT '',
    expires_at    TIMESTAMPTZ NOT NULL,
    consumed_at   TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**指纹** = `sha256(finding_id | 规范化 tool_name | 规范化 arguments | 允许的 host 集合 | 等级)`。规范化只做保守变换（去空白、排序 JSON key、小写方法名），不做语义归一——指纹应当**近乎精确匹配**，宁可多批几次也不要一次批一片。

闸门顺序（`guard.PreToolUse`，即 `applyIntercept` 之前）：

1. 规则命中 `deny` → **先看凭证**：有未消费、未过期、指纹匹配、host 在集合内、等级 ≤ `max_level` 的批准 → 放行并立即标记 `consumed`（一次性），写审计。
2. 否则按 deny 返回，message 指引提案。
3. 规则未命中 → 走现有 JEV judge 逻辑（不动）。

`consumed` 必须是原子的（`UPDATE ... WHERE status='active' AND expires_at > now() RETURNING`），否则并发 worker 能蹭同一张凭证。

### 4.3 需要改动的落点

- `guard/guard.go`：`preToolUse` 里插入凭证匹配（在 `applyIntercept` 结果之前）。
- `db/db.go`：新增规则组播种；新增 `exploit_approvals` 的 CRUD。
- `db/schema.sql`：两张新表 + `findings.verify_level` / `findings.impact_observed`。
- 规则修改要能被 `intercept_rules` 的 UI 覆盖（已有能力），但内置规则组默认启用，允许用户按项目关闭（关闭要在审计里留痕）。

## 5. 提案模型（"理论操作"的载体）

### 5.1 工具 `propose_escalation`

绑定到 `worker`/`mainagent`/`pentest`（seed 进 `agent/toolcatalog.go` 的 `BuiltinToolSeeds`）。参数：

```jsonc
{
  "finding_id": 123,
  "level": "L3",
  "title": "验证命令执行影响面：读取数据库配置",
  "objective": "确认当前 RCE 能否读到应用配置，从而评估凭据泄露风险",
  "preconditions": ["已确认 /upload 存在命令执行", "目标可写 /tmp"],
  "steps": ["1. 执行 cat /app/config.yml", "2. 记录返回的数据库地址"],  // Markdown 理论步骤，不执行
  "expected_impact": "可能读到生产数据库凭据",
  "blast_radius": "目标应用服务进程权限内可读的一切文件",
  "stop_conditions": ["返回内容含凭据即刻停止并截图", "目标响应 > 3s 立刻停止"],
  "rollback": "只读操作，无残留；如写入文件需在执行后删除",
  "alternative": "先尝试只读 /proc/self/cmdline 确认工作目录，不触碰配置",
  "intent_id": 456
}
```

产物：`finding_escalations` 一行，`status=proposed`，并在 finding 上打标（`impact_observed=theoretical`）。**工具本身不执行任何危险动作**，只写库。

### 5.2 表结构

```sql
CREATE TABLE IF NOT EXISTS finding_escalations (
    id                BIGSERIAL PRIMARY KEY,
    project_id        BIGINT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    finding_id        BIGINT NOT NULL,
    task_id           BIGINT,
    level             TEXT NOT NULL CHECK (level IN ('L2','L3')),
    title             TEXT NOT NULL,
    objective         TEXT NOT NULL DEFAULT '',
    preconditions     TEXT[] NOT NULL DEFAULT '{}',
    steps             TEXT NOT NULL,            -- Markdown 理论步骤
    expected_impact   TEXT NOT NULL DEFAULT '',
    blast_radius      TEXT NOT NULL DEFAULT '',
    stop_conditions   TEXT[] NOT NULL DEFAULT '{}',
    rollback_plan     TEXT NOT NULL DEFAULT '',
    alternative       TEXT NOT NULL DEFAULT '',
    proposed_by       TEXT NOT NULL DEFAULT '',  -- agent key
    status            TEXT NOT NULL DEFAULT 'proposed'
                      CHECK (status IN ('proposed','approved','rejected','running','executed','failed','cancelled','expired')),
    decided_by        TEXT NOT NULL DEFAULT '',
    decided_at        TIMESTAMPTZ,
    decision_note     TEXT NOT NULL DEFAULT '',
    expires_at        TIMESTAMPTZ,
    run_id            BIGINT,
    impact_observed   TEXT NOT NULL DEFAULT '',
    created_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

`escalation_runs`（可选，P2）：记录执行窗口、速率、实际请求数、熔断原因、产出证据。

## 6. 执行层：受控执行器

批准后有两条路，建议**默认走 A**：

**A. 平台受控执行（推荐）**
- 批准 → 创建 `escalation_run`，把提案的 `steps` 转成一条特殊 intent 插进该任务的探索图（`intent_id` 带 `escalation:<id>` 标记），由受限 worker 执行。
- 受限 worker 的约束：
  - 只允许批准的指纹（`exploit_approvals`），每个指纹一次性；
  - **执行窗口**默认 10 分钟，超窗自动取消；
  - **速率/并发**：每 target 1 rps、并发 1、单请求超时 15s、body < 256KB；
  - **熔断**：按目标 host 判定（见 §6.1），只作用于这一次执行；
  - 每步执行后立刻写回 finding（`impact_observed` + traffic 证据绑定），不等全部跑完。
- 执行结束回写 `finding_escalations.status`（`executed`/`failed`/`cancelled`），发通知。

**B. 导出命令人工执行**
- 详情页提供"复制命令"，由测试人员在测试窗口自己跑。
- 缺点：绕过审计、绕过熔断、平台不知道结果；只作为兜底，不建议默认。

两种都要求：**执行前把步骤展示给人看，执行后把结果写回 finding**。

### 6.1 保护范围：只在"获批的扩展执行"里生效，不碰探索

原则：**探索能力不做任何自动降级**。ARTEX 的核心竞争力是"能打、打得深"，任何会让 agent 在探索途中被自动掐断的机制都不应该默认开启。

| 控制 | 生效范围 | 默认 | 对探索能力的影响 |
|---|---|---|---|
| 破坏性动作拦截规则（§4.1） | 全任务 | 开 | 只拦明确的破坏性动作，正常探测不受影响 |
| 破坏性动作需审批（§4.2 凭证） | 全任务 | 开 | 高影响动作必须走提案，正常探测不受影响 |
| 静态速率/体积上限 | 可配 | **关**（或给很宽松的默认值） | 无（不基于反馈，不随目标状态变化） |
| 执行窗口 + 运行级熔断 | 仅 `escalation_run` | 开 | **无**，探索期根本不在这个路径上 |
| 目标健康监测 | 全任务 | **只告警** | 无（不拦任何调用） |
| 探索期 host 冷却 | 全任务 | **关**，项目级可选开 | 开启后才会拦，默认不拦 |

#### 为什么熔断只保留在获批执行里

获批执行是唯一"人明确要求做有影响的事"的场景：执行窗口短、动作是事先批准的、人就在页面上看着。这时候自动收手是帮忙，不是添乱——而且它保护的是**客户的目标**，不是 ARTEX 的能力。

#### 探索期只告警，不拦

探索期的目标健康信号照样采集（5xx 比例、连接失败、时延、响应体突变），但**默认只做三件事**：

1. 在任务详情和漏洞详情里显示"目标健康"曲线，跳变处打点；
2. 命中阈值时给任务打一个 `target_stress` 标记并发通知，让人决定要不要暂停；
3. 把受影响的请求 ID 存进 finding 的证据里——这对写报告很有用（"这条漏洞可能对目标产生压力，建议在低峰期复测"）。

不拦的理由就是你说的：探索期自动拦会直接削弱渗透能力，而且阈值判定天然有误报（目标本来就在抖、共享入口的正常波动），误报的代价是漏掉真漏洞。

#### 需要新增的最小改动

`exchanges` 目前只有 `status`/`resp_len`/`ts`，**没有耗时**。加一列 `dur_ms`（代理本来就知道往返时间），健康和告警才有可靠依据；不加也能量 5xx 和连接失败，只是会晚一步发现"正在变慢但还没挂"。

#### 确实要"一键止血"时

人工暂停任务（`tasks.paused`）保留，作为紧急按钮。注意它的真实语义（`server/engine.go` 的 planner/worker 循环检查 `IsPaused`）：

1. **任务级**：同任务几个 worker 可能分别在打不同 host，停整个任务会误伤其它 host。
2. **不中断正在跑的命令**：`IsPaused` 只在循环边界生效，已在执行的那一轮会跑完。真要掐断，需要给 agent 一个可取消的 context（扩展执行天然有；探索 worker 需补 stop 信号，列进 P2）。
3. **不影响其它任务**：每个 task 有独立的 planner + N 个 worker 循环。

## 9. 分阶段落地

| 阶段 | 内容 | 工作量 | 价值 |
|---|---|---|---|
| **P0 止血** | worker/main 提示词最小化章节 + 8–10 条高影响拦截规则（deny + 指引）+ `findings.verify_level` 落库与徽章 + 约束注入影响上限 | 1–2 天 | 立刻减少"为了证明而打穿"的行为；规则命中可审计 |
| **P1 提案闭环** | `propose_escalation` 工具 + `finding_escalations` + 详情页「利用验证」Tab + 审批/拒绝 API（批准后**人工执行**） | 3–5 天 | "理论 vs 执行"的边界立住，人能看见每条提案 |
| **P2 受控执行** | 审批凭证 + guard 消费 + 受控执行器 + 窗口/速率/熔断 + 执行记录 | 5–8 天 | 硬保证：批准之外的动作执行不了，批准之内只跑一次 |
| **P3 治理** | 度量（等级分布、审批时长、熔断次数、误报率）、项目级策略模板、JEV judge 并入"最小化"判定、报告/导出完善 | 持续 | 可持续调优，避免审批疲劳 |

P0 只改提示词和规则就能上线；P1 是需求里"审核并确认执行"的最小可用形态；P2 才提供技术保证。

## 10. 验收标准

- 单测：凭证一次性消费（第二次拒绝）、过期拒绝、跨项目拒绝、指纹不匹配拒绝；规则命中 deny 时 message 含提案指引；`verify_level` 默认值与回填。
- 集成：L0 验证流程不触发任何高影响规则；L3 动作无凭证→deny；批准后仅该指纹放行一次；执行超窗自动取消；熔断触发后剩余步骤 `skipped`。
- 熔断单测：获批执行中 5xx 超阈值 → 本次运行停止、剩余步骤 `skipped`；同一场景在探索期只产生 `target_stress` 告警、**不拦任何调用**（除非项目显式开启 host 冷却）。
- 手工验收：任选一个注入点，要求 agent"证明它存在"，产出必须是布尔/报错级证据；让它"扩大影响"，产出必须是提案而不是执行。
- 度量基线：整改前后各取 20 个任务，统计 `impact_observed` 分布、目标 5xx 率、被规则拦截次数。

## 11. 风险与取舍

1. **误报会挡住正常验证**：规则要窄（宁可漏，先靠提示词），message 必须给出获批路径；每条规则都要有"关闭"开关且关闭留痕。
2. **审批疲劳**：按 finding 聚合（一次批准覆盖同类动作）、提供"仅保留理论"一键、默认最小化减少提案量。
3. **模型不听话**：闸门兜底；JEV judge 的审查策略里加一条"高影响动作须有凭证"，与规则形成双保险。
4. **理论质量参差**：提案 schema 强制 `steps`/`stop_conditions`/`rollback`/`alternative`，空字段直接拒绝入库。
5. **"自动执行"的信任成本**：先给 P1（人工执行）+ P2（受控执行）两档开关，默认开 P2 的窗口与熔断，允许项目级关闭自动执行。
6. **资产信息不足导致 blast radius 失真**：用已采集的资产/企业范围做提示，标"未知"而不是"无影响"。

## 12. 需要拍板的决策点

1. 任务默认影响上限：**L1**（推荐）还是 L0？
2. L3 审批是否要求二次确认（输入目标域名）+ 双人复核？
3. 批准后默认**平台受控执行**（推荐，可审计）还是导出命令人工执行？
4. 探索期是否需要"目标被打挂时自动停"？推荐**默认关、只告警**（见 §6.1），需要时按项目开启；执行期的熔断保持开启。
5. 老数据回填：存量 findings 的 `verify_level` 默认 `standard`（历史无法判定）还是 `unknown`？
