# ARTEX 白盒驱动测试转型设计方案

- 日期：2026-11-20
- 修订：2026-11-23（确立“统一控制面 + 异构执行器 + 程序硬护栏”架构：白盒审计融入 MainAgent，Planner 统筹全流程，Engine 统一执行与生命周期）
- 状态：设计方案；第 1–3 步已完成，第 4–8 步按 2026-11-23 修订后的统一控制面架构分阶段实施。
- 范围：任务创建、画像知识库、覆盖计划、白盒审计、动态测试、增量探索、完成判定、前端和兼容迁移。
- 前置基础：[多语言白盒审计设计方案](multilang-whitebox-audit-design.md)。已有多语言审计能力是本方案的执行基础，不等同于本方案中的任务级覆盖体系。

## 1. 转型目标与约束

ARTEX 从以用户目标和意图发散为主的黑盒探索，转为以下工作方式：

1. 用户提供源码或 Java 部署包，以及业务和测试环境信息。
2. 平台检查材料，建立明确的代码、资产、环境和版本清单。
3. 构建有证据、可查询、可修订的任务画像知识库。
4. 根据画像生成覆盖计划，以白盒分析指导动态测试。
5. 动态测试持续补充画像、产生有依据的新测试方向。
6. 由程序根据覆盖义务和执行证据判定任务是否完成。

Agent 的持续目标是尽可能发现真实、独立、有影响的漏洞。任务完成条件由用户自定义的结果目标，转为本轮范围内的覆盖义务全部满足。

### 1.1 必须保持的约束

- 不修改预算默认值、预算判断或相关界面；默认不限预算是用户的明确选择。
- 不通过漏洞类型白名单限定模型的审计能力。类别由模型根据实际问题自行命名，平台校验证据与执行范围。
- 保留已有 A/B/C 分级登记、候选修复、去重、证据历史、报告和复测能力。
- 静态分析不等于动态验证；一次未复现不等于漏洞不存在或已经修复。
- 动态执行仅针对任务授权的隔离测试环境，不针对在线或生产系统。外部依赖可以进入画像，但不能自动扩展测试授权。
- 既有任务和既有数据继续可读、可运行，不把旧覆盖语义强行改成新覆盖语义。

### 1.2 “全覆盖”的定义

全覆盖指：**在明确的代码版本、环境版本、测试范围和覆盖标准下，所有适用的必需测试义务均已完成，并具有符合要求的证据。**

它不表示穷尽所有执行路径，也不表示证明系统不存在漏洞。必须分别展示已完成检查、未覆盖内容、未知条件、阻塞与范围例外。

“尽可能多挖漏洞”是持续工作目标，不是按 Finding 数量判定成功。原始发现数量不能成为奖励或终止条件，以免鼓励重复和低质量登记。

## 2. 现有基础与转型差距

以下判断基于方案讨论时的代码。实施时应再次核对具体函数与调用关系。

| 现有能力 | 新架构中的用途 | 必要变化 |
| --- | --- | --- |
| 代码上传、不可变版本、服务发现 | 建立代码清单与版本基线 | 增加启动前材料检查，覆盖非服务代码 |
| Java/Python/C 审计、JavaCodeDB | 作为 `Engine` 内的批量白盒执行内核（`code_audit_batch`） | 从独立轮询队列与独立聊天入口下沉为受 `Intent` 驱动的受控执行器，支持非服务模块、分片检查点续跑与分片级增量唤醒 Planner |
| 文件读取/分析台账、补审、收尾扫描 | 提供静态执行证据 | 接入任务级覆盖验收 |
| Planner、Worker、意图图 | 唯一全局统筹大脑与统一执行控制面 | 白盒评估模式下接收轮次级画像与覆盖义务切片；按 `Intent` 执行模式路由至批量白盒、只读白盒调查或动态验证执行器 |
| MainAgent 与白盒聊天 | 统一人工交互与操舵入口 | 评估模式将 `whitebox_audit` 能力并入 `MainAgent` 并隐藏独立白盒聊天入口；传统模式保留旧入口兼容 |
| 资产图与任务资产隔离 | 展示对象、限制可见范围 | 增加代码到实例、入口到处理函数等关系 |
| Findings、A/B/C、报告和复测 | 保存静态线索和动态验证 | 串联候选、尝试、证据与结论 |
| 暂停、取消、恢复、准入 | 控制执行生命周期 | 所有白盒与动态工作统一经 `Engine` 的 `Intent`/`workCtx` 调度，天然共享暂停、恢复、取消、超时、删除排水与并发槽位 |

### 2.1 覆盖统计不能直接复用为完成条件

`db/task_scope.go` 中的资产覆盖是近似指标：资产关联过 fact 节点即可算作已测试。`db/task_assets_context.go` 还会纳入直接关联任务的资产与事实。这适合展示探索进展，不足以证明当前环境和当前版本已完成规定测试。

`server/code_audit_coverage.go` 的文件台账要求实际读取并由模型声明分析完成，且支持补审和收尾扫描。这是可复用的执行证据，但不是全文件语义验证或任务级动态覆盖的证明。

### 2.2 可部署服务与待审代码模块需要分开

当前服务发现会把共享库、父工程等判定为非服务。分类本身合理，但白盒主导任务仍需覆盖其中的自研代码。

新模型必须区分：

- 可部署服务：对应运行实例和对外能力。
- 待审代码模块：可以是服务、共享库、公共鉴权代码、协议适配代码或其他自研模块。

不能为了审计共享库而把它伪装成独立服务，也不能因为它不是服务就忽略它。

### 2.3 从双控制面走向“统一控制面 + 异构执行器”

当前任务完成仍存在目标证明、无开放目标且无活动意图可提前结束任务，以及意图来源关系并非可执行依赖等问题；同时，原有 `server/java_code_audit.go`（`startTaskCodeAuditWorkers` 独立后台轮询队列）与 `server/task_code_audit_chat.go`（`whitebox_audit` 独立会话）构成游离于 `MainAgent`、`Planner` 与 `Engine` 之外的第二套控制面，容易导致白盒与动态上下文割裂，并发配额、暂停、取消、超时与完成对账难以统一收口。

白盒评估模式不维持双引擎并跑，也不把大仓库全量审计退化为无分片的通用聊天 Worker，而是采用**“统一控制面 + 异构执行器 + 程序硬护栏”**：由 `MainAgent` 统一承接人工交互、由 `Planner` 全局统筹“白盒↔动态”调度顺序、由 `Engine` 通过 `Intent` 统一调度三类异构执行器（`code_audit_batch` / `code_investigate` / `dynamic_verify`），并由程序守住分母、证据与完成三条底线。

## 3. 任务创建与生命周期

### 3.1 用户输入

| 输入 | 要求与用途 |
| --- | --- |
| 源码或 Java 部署包 | 必需；建立可审计版本 |
| 业务说明 | 模块、核心对象、敏感数据、角色、租户与流程 |
| 环境地址 | 测试入口、内部服务、网关、管理端等 |
| SSH 或其他环境访问方式 | 可选；用于授权环境的部署与运行信息采集 |
| 测试身份 | 匿名、普通用户、管理员、不同租户等可用身份 |
| 测试范围与操作约束 | 可测试对象、允许与禁止操作 |
| 模型配置与源码发送确认 | 沿用现有模型配置和源码分析确认机制 |

用户不再需要设置“获得某种权限”一类的最终结果目标。业务重点可用于调整优先级，但不能替代必需覆盖。

可从描述中提取结构化环境信息，同时保留原文出处和不确定性。描述中出现地址或凭证，不应直接解释为对该对象的一切测试操作均获授权。

### 3.2 两段式创建

1. 创建草稿、取得任务 ID，上传代码并填写环境信息。
2. 用户启动任务时进行材料检查，检查通过后进入画像构建。

当前上传接口要求任务先存在，因此草稿机制应放在持久化创建与启动编排之间。页面创建和 Agent 创建任务都必须经过相同流程。

### 3.3 阶段与运行状态

建议新增 `assessment_phase`，独立表达：

1. 材料检查。
2. 画像构建。
3. 覆盖规划。
4. 执行与探索。
5. 收尾对账。
6. 完成。

暂停、等待凭证、环境不可达、执行失败等另存为运行状态或阻塞原因，避免把阶段和所有状态组合编码为一个字段。

### 3.4 材料检查

启动前至少确认：

- 文件可读取、可解包，确实包含支持的源码或 Java 类，而不只是扩展名匹配。
- 文件/类清单能够建立，读取失败和无法分类的对象不会被静默忽略。
- Java 部署包所需索引、反编译能力可用。
- 至少存在一个有效审计对象；不要求该对象一定能独立部署。
- 要求动态测试的任务具有足够环境输入，可以生成环境核实工作。

只有源码而没有环境时，可以推进静态部分，但不能把整个动态测试任务标为完成。若支持纯离线任务，应使用显式的离线覆盖标准和完成结果。

## 4. 任务画像知识库

### 4.1 内容模型

| 维度 | 内容 |
| --- | --- |
| 业务结构 | 模块、核心对象、敏感数据、关键流程、角色与租户 |
| 代码结构 | 仓库、模块、共享库、语言、构建单元、入口、配置和依赖 |
| 部署架构 | 应用、实例、容器/主机、启动参数、路径与配置来源 |
| 网络架构 | 域名、地址、端口、网关、代理、区域与已知访问路径 |
| 技术架构 | 数据库、缓存、消息队列、对象存储、调度与检索能力 |
| 开发框架 | Web/RPC、路由装配、ORM、中间件、序列化与模板机制 |
| 认证机制 | 登录、会话、Token、SSO、服务身份与密钥引用 |
| 鉴权机制 | 角色、资源归属、租户隔离、权限决策点与策略继承 |
| 南北向与东西向对接 | 外部入口、外部依赖、内部调用、回调与异步消息 |
| 协议适配 | 协议类型、转换位置、字段映射和身份传递 |
| 版本对应关系 | 上传材料与实际运行实例的关联及其证据 |
| 未知项与冲突 | 缺材料、推断关系、矛盾配置和未核实行为 |

业务对象与权限语义是必要知识。只知道框架、数据库与缓存的名称，不足以进行资源归属、租户隔离和业务流程测试。

### 4.2 每条知识的记录要求

每条属性或关系断言至少保存：

- 主体、关系/属性、客体或值。
- 来源类型：用户声明、静态提取、运行观察、模型推断。
- 证据引用。
- 适用代码版本、环境与配置。
- 确认状态、冲突状态和未知条件。
- 采集时间与产生该知识的执行记录。

源码显示 Token 校验、运行入口却可以匿名访问时，要保留两条事实并核实入口、版本、配置和代理路径。不能简单用某种来源统一覆盖另一种来源。

密码、私钥和会话 Token 不进入普通画像文本或通用模型上下文。画像保存身份语义及凭证引用；执行通过受控方式取得必要凭证。

### 4.3 存储与查询

现有 `task_intelligence` 继续用于凭证、线索和敏感数据情报。另建画像事实和关系结构，不将整个架构知识库塞入长文本情报。

第一版使用 PostgreSQL 关系表与 JSONB，提供按实体、关系、版本和证据的查询。向量检索可以后续补充，但不能作为覆盖状态或完成判定的数据依据。

文字画像报告是结构化知识的展示投影，不是唯一事实来源。

### 4.4 构建过程

1. **确定性清点：** 收集文件、类、构建清单、部署配置、协议描述，形成版本清单。
2. **结构提取：** 识别模块、路由、处理函数、认证装配、依赖和配置引用；可靠可解析的内容由程序提取。
3. **Agent 关联：** 阅读必要代码，解释业务结构、隐式装配和跨模块关系，输出带引用的断言。
4. **环境核实：** 在授权环境中通过响应、流量、运行信息或配置观察核实部署情况。
5. **形成初始版本：** 固定画像快照，保留未知项及其后续工作。

初始画像达到“清单已建立、主要模块已识别、环境和范围已明确、关键未知项已登记”即可支撑后续工作。不要要求一切信息都已确定才开始审计；只阻塞受未知条件影响的工作。

画像更新必须进行影响分析。例如认证链变化，要重新审视依赖该认证链的入口与证据。

## 5. 覆盖图与覆盖义务

### 5.1 三个逻辑视图

| 视图 | 回答的问题 |
| --- | --- |
| 目标画像图 | 系统由什么组成，对象之间是什么关系 |
| 覆盖计划图 | 每个对象需要完成什么检查，有哪些前置依赖 |
| 执行与证据图 | 执行了什么，得到什么证据，形成什么结论 |

三者复用实体标识和证据引用，但不能用一个“已探索”状态代替不同含义。

### 5.2 覆盖义务定义

覆盖义务是为了说明某个对象已按本轮标准接受测试，必须完成的一项具体工作。它至少包括：

- 目标对象及版本。
- 检查目的。
- 适用环境、身份与业务上下文。
- 前置依赖。
- 所需执行能力。
- 验收证据要求。
- 执行尝试、当前状态和阻塞原因。
- 关联假设、候选漏洞与 Finding。

覆盖义务约束“检查哪些对象、需要什么证据”，不限定模型只能发现哪些漏洞类型。

### 5.3 第一版覆盖维度

| 维度 | 典型对象 | 完成要求 |
| --- | --- | --- |
| 代码审计 | 自研模块、生产文件、Java 应用类 | 有阅读和分析记录，完成必要补审 |
| 配置审计 | 安全配置、部署配置、协议映射 | 分析有效配置及影响，区分声明与生效情况 |
| 入口测试 | HTTP、RPC、消息消费者、任务入口 | 建立入口上下文，完成适用运行测试并保存结果 |
| 身份与资源关系 | 角色、租户、对象归属、业务状态 | 对相关访问关系进行有依据的测试 |
| 跨模块链路 | 服务调用、回调、消息、协议转换 | 检查数据、身份与控制条件的跨环节传递 |
| 运行资产 | 范围内网关、实例、数据库等 | 完成与其角色相关的检查；不能检查时记录阻塞 |
| 漏洞假设 | 静态候选、动态异常、配置冲突 | 形成支持、反证、未复现或阻塞等有证据的处置 |

### 5.4 避免遗漏和组合爆炸

- 没有静态候选的入口也必须有适用的动态测试义务，避免退化为静态扫描后的验证器。
- 共享库和公共安全代码必须被清点。同一份代码可复用静态分析，但不同调用位置的运行条件仍需分别考虑。
- 按实际权限规则、控制实现和业务状态划分等价组，不机械展开入口、角色、租户和状态的完整笛卡尔积。
- 展示采用的代表场景和未覆盖组合，不能为减少数量随意合并不同权限规则。
- 第一阶段使用文件/类级静态覆盖，逐步增加函数、入口和关系级覆盖，不宣称任意语言的完整调用图与全路径分析。
- 不能读取或解析的对象形成缺口，不能自动从分母消失。

## 6. 状态、覆盖计算与完成判定

### 6.1 覆盖义务状态

建议状态为：`pending`、`ready`、`running`、`satisfied`、`blocked`、`stale`、`not_applicable`。

- `satisfied`：完成规定检查；可以发现漏洞，也可以没有发现问题。
- `blocked`：前提缺失、环境不可达等，不计入已覆盖。
- `stale`：材料、环境或关键画像变化，原有证据不再适用。
- `not_applicable`：有可审计的不适用依据，不能由 Agent 为提高覆盖率任意设置。

执行失败、超时、跳过和接受暂不测试都不等于已覆盖。用户接受例外后，可结束为部分完成，或显式修改范围并生成范围新版本。

### 6.2 覆盖计算

各维度分别计算适用的必需义务及其满足数量。无适用对象时显示“不适用”，不显示 100%。

总览可以显示加权指标，但完成判定必须逐项检查必需义务，不能由高权重维度掩盖其他维度缺口。

### 6.3 任务完成的必要条件

1. 材料清单已对账，没有未处理的读取、解析或分类缺口。
2. 当前范围和版本下全部必需义务已经满足。
3. 没有正在执行或等待派发的必需工作（包括各类评估 Intent 及其关联的在跑白盒审计运行；同时兼容检查遗留或传统模式白盒队列）。
4. 已产生且需要处理的漏洞假设已经得到有依据的处置。
5. 完成跨模块收尾检查。
6. 没有未处理的新资产、新入口、知识冲突或证据失效事件。
7. 最终结果记录本轮版本、范围、标准和限制。

任务完成由程序统一判定。Planner 和 Worker 只能提交工作、证据和结论建议，不能直接把任务标为全覆盖完成。

### 6.4 收尾对账与新轮次

最终对账读取一致的计划版本和执行状态，确认没有新覆盖变化，再以事务或版本条件提交完成结果，避免新发现与完成写入并发造成提前结束。

完成后出现新代码或部署版本，应创建新评估轮次，重新打开受影响的义务。历史轮次保持原有范围和结果，不被覆盖。

## 7. 白盒指导的动态探索

### 7.1 两条工作线

- **基础覆盖线：** 保证所有范围内对象接受规定程度的检查。
- **深入探索线：** 围绕静态线索、运行异常、身份差异与跨模块连接继续调查。

优先级综合未覆盖重要入口、关键业务和数据路径、真实代码线索、能够解除多个阻塞的前置工作以及等待时长。不能让少量高价值线索长期挤占普通对象的覆盖机会。

### 7.2 动态工作单

每项工作至少包含：

- 要回答的问题或验证的假设。
- 目标入口、资产与允许范围。
- 对应代码位置和画像快照。
- 身份、租户、业务状态及前置条件。
- 预期观察行为和必要对照。
- 证据采集方式。
- 可能副作用、恢复要求与停止条件。
- 结果分类。

结果区分支持假设、反证、未复现、环境不匹配、依赖缺失和执行失败。单次异常响应不能自动确认漏洞；单次未复现不能自动否定漏洞。

### 7.3 反馈闭环

动态测试发现的新信息返回画像：

- 范围内新对象：更新清单并产生义务。
- 范围外依赖：只作为上下文记录，不扩大授权。
- 无法关联源码的运行对象：保留明确缺口，不从图中隐藏。
- 配置、身份或部署冲突：更新画像并使受影响证据失效。

例如，源码从 Token 获取租户，但对象查询是否保留租户约束不清楚，可生成身份与资源归属验证工作，关联请求响应、对象状态与代码证据。若发现部署版本不同，先登记版本差异，不能把结果直接归因于上传源码。

### 7.4 静态与动态职责隔离

职责隔离落在**三类执行器的工具权限边界**，而不割裂调度控制面。所有工作均作为 `Intent` 由统一控制面调度，但各执行器严格限定自身工具集：

- `code_audit_batch`（批量静态审计内核）：运行于 `Engine` 的 `workCtx` 内，直接复用 `server/java_code_audit.go` 的分片推进、断点续跑（`next_file_index` / `next_class_index`）、JavaCodeDB 反编译、真实读取台账（`server/code_audit_coverage.go`）、A/B/C 分级、候选修复、补审与收尾扫描内核；只允许读取源码与画像，严格无 Bash 与网络权限。
- `code_investigate`（定向只读白盒 Worker）：轻量级只读白盒 `agent.Worker`，仅挂载只读代码、JavaCodeDB、画像与覆盖台账工具，严格无 Bash、无网络请求，专责跨模块调用链追踪、认证链澄清、配置冲突核查与动态异常后的反向查码。
- `dynamic_verify`（动态验证 Worker）：现有动态 `agent.Worker`（Bash/HTTP/流量/浏览器 + 范围守卫 + 拦截审查 + 只读代码切片查询），使用已有范围、操作约束、拦截和最小化验证机制，负责环境核实、无静态候选入口的基础动态测试、静态线索复现与身份/租户访问控制验证。

A/B/C 是静态登记层次，动态验证结果另行记录。保留未确认线索及其不确定性，避免静态登记自动升级为已利用成功。

## 8. Agent 与程序的分工

围绕人工交互、全局统筹、异构执行和程序护栏划界，不为每种架构维度单建独立 Agent。

### 8.1 核心架构与职责分工

| 职责 | 承担方 | 核心边界 |
| --- | --- | --- |
| 材料检查、清单与版本绑定 | 程序 | 启动前阻塞无有效材料；确定性生成模块、配置与覆盖分母，Planner 不可删除 |
| 画像理解与证据关联 | 确定性提取器 + 调查执行 | 可解析结构由程序提取并绑定证据引用；隐式关系按来源与冲突状态受控写入 |
| 人工交互、查询与任务操舵 | `MainAgent` | 评估模式吸收白盒查询、优先级引导、确认后直投及约束/例外登记 |
| 全局覆盖统筹与跨端调度 | `Planner` | 读取轮次级画像与覆盖切片，统筹白盒与动态优先级并派发 `Intent`；只可申请收尾 |
| 全量/分模块静态审计 | `code_audit_batch` 执行器 | 在 `Engine` `workCtx` 内运行确定性分片审计内核；只读源码，断点续跑 |
| 定向只读代码/调用链调查 | `code_investigate` Worker | 挂载只读代码/JavaCodeDB/画像工具，严禁 Bash 与网络请求 |
| 环境核实与动态漏洞验证 | `dynamic_verify` Worker | 按结构化工作单与范围/拦截守卫执行运行态测试，附只读代码切片查询 |
| 证据入库、验收与任务完成 | 统一程序护栏 | 校验真实读取台账与动态证据、推进义务状态，原子提交轮次完成 |

### 8.2 统一意图路由、并发软配额与分片续跑

- **统一 Intent 路由与尝试绑定**：意图（`exploration_nodes` `kind='intent'`）继续作为最小调度单元，但与 `task_test_attempts` 一起显式携带 `execution_mode`（`code_audit_batch` / `code_investigate` / `dynamic_verify`）、`obligation_id`、`round_id`、`attempt_id`、`profile_version` 与 `idempotency_key`。`Engine.runIntent` 按 `execution_mode` 路由到对应执行器，并在同一 `workCtx` 内提供 `steer_work`、`kill_work`、暂停、恢复、取消、超时、删除排水与重试保护。现有证据来源边不能直接当作执行依赖。白盒评估模式（`assessment_mode=true`）不再由 `startTaskCodeAuditWorkers` 独立后台轮询驱动。
- **共享 `WorkerSlots` 与软配额保护**：三类执行器共享 `Engine` 总 `WorkerSlots` 池并严格受任务总并发上限约束。当可用槽位 `slots >= 2` 时，`code_audit_batch` 并发上限为 `slots - 1`，至少保留 1 个槽位给 `dynamic_verify` 与 `code_investigate`，避免大批量静态扫描长期占满槽位而饿死动态验证与定向查码；当 `slots == 1` 时由 `Planner` 按优先级与等待时长交替调度。
- **模块级 Intent + 检查点续跑 + 分片级增量唤醒**：`code_audit_batch` 按模块/共享库（或超大模块的顶层子包）派发为模块级 `Intent`，执行器内部沿用分片推进并关联 `code_audit_run_id` 持久化 `next_file_index` / `next_class_index` 与已读台账。**每完成一个分片即落库已读台账与 A/B/C 候选，并触发轻量评估事件唤醒 `Planner`**，使 `Planner` 在大模块仍处于静态审计中时即可并发派发 `dynamic_verify` 实现“边审边测”。因暂停、取消、超时或服务重启中断 `workCtx` 后保留检查点，恢复执行同一义务或重派时从断点续跑，不重头重复审计。

### 8.3 Planner 统筹协议与程序硬护栏

- **恢复评估 Planner 统筹**：取消 `server/engine.go` 对运行态 `AssessmentMode` 的 `planner.Plan` 拦截，由 `Planner` 担任白盒与动态全流程的唯一全局调度大脑；草稿态任务仍严格禁止进入 `Planner`。
- **轮次级受限上下文与收敛写操作**：每轮规划仅向 `Planner` 提供绑定当前 `round_id` / `profile_version` 的结构化上下文切片（待办/就绪/阻塞/失效覆盖义务、模块审计覆盖台账、最新静态候选与动态尝试、画像未知项与冲突、用户提示与操作约束、在跑 Intent 状态）。`Planner` 的写操作收敛为：派发绑定 `obligation_id` 与 `execution_mode` 的 `Intent`、登记有证据依据的深入探索义务、写入带来源引用的画像断言、对在跑 Intent 执行 `steer_work` / `kill_work`，以及在判定本轮就绪后发起 `request_assessment_completion`。
- **三条程序硬护栏**：
  1. **分母护栏**：材料检查、代码/配置清单与必需基础覆盖义务由程序确定性生成，`Planner` 可调整优先级与增补深入探索义务，但禁止删除或随意将必需义务标为 `not_applicable`。
  2. **证据护栏**：文件真实读取/补审台账校验、A/B/C 静态分级规范、动态执行证据核验及覆盖义务状态推进均由程序强制校验，`Planner` 不能跳过证据直接标为 `satisfied`。
  3. **完成护栏**：`Planner` 只能通过 `request_assessment_completion` 申请收尾对账，禁止直接将任务标为 `done`；仅程序契约（`AssessmentCompletionCheck` / `CompleteAssessment`）可在确认一致后原子提交完成。

### 8.4 MainAgent 融合、生命周期收口与传统模式兼容

- **评估模式收敛为唯一 `MainAgent` 入口（`assessment_mode=true`）**：将原 `whitebox_audit` 的能力并入 `MainAgent`，统一承担代码服务/模块与审计覆盖进度查询、白盒与动态优先级引导（向 `Planner` 注入提示）、用户明确确认源码发送后的白盒审计或定向查码直投、`steer_work` 实时纠偏以及操作约束/范围例外登记；前端任务详情「会话」区域隐藏独立的「白盒审计 Agent」聊天入口。
- **传统模式保持兼容（`assessment_mode=false`）**：完整保留原有 `whitebox_audit` 独立会话入口、手动逐服务白盒审计流程及既有历史对话与审计运行记录，确保老任务继续可读、可运行。
- **单协调器与生命期收口约束**：当前普通 Worker 依赖 CAS 所有权与启动恢复，并非完整的分布式租约；第一版保持单协调器，增加 `attempt_id` 标识与迟到结果写入保护，多执行节点再引入续租与失效接管。暂停、取消与完成必须等待必要的最终写入、分片检查点落盘与执行收口，保留已有删除保护和执行准入，不只取消内存中的 context。

## 9. 建议的数据模型

以下名称是设计建议，不表示这些表已经存在，也不要求一次性实现全部表。

| 数据组 | 职责 |
| --- | --- |
| `task_assessment_rounds` | 绑定本轮代码、环境、范围、标准版本与完成记录 |
| `task_target_entities` | 表达模块、实例、入口、身份、业务对象等，关联既有资产 ID |
| `task_profile_claims` | 属性和关系断言、证据、来源、有效版本、未知与冲突 |
| `task_evidence_refs` | 代码范围、反编译来源、流量、执行输出等引用 |
| `task_coverage_obligations` | 要求、依赖、验收规则、状态与失效原因 |
| `task_test_attempts` | 关联意图/白盒运行，保存版本、尝试标识、输出和验收 |
| `task_assessment_events` | 新资产、画像变化、失效等可靠事件，驱动增量调度 |

`Intent`（`exploration_nodes` `kind='intent'`）负载与 `task_test_attempts` 统一关联 `execution_mode`（`code_audit_batch` / `code_investigate` / `dynamic_verify`）、`obligation_id`、`round_id`、`attempt_id`、`idempotency_key` 与 `profile_version`，并为 `code_audit_batch` 绑定可续跑的 `code_audit_run_id` 检查点引用。第 1–3 步已落库的评估轮次、目标实体、证据引用与画像断言表在此基础上平滑扩展，无需推翻重构。

审计运行应允许绑定通用代码目标。保留历史 `code_service_id` 关联，新目标可以是不可独立部署的模块；查询、归档和 Finding 关联需要同步兼容。

一次执行不应接收整个知识库。按目标查询相关模块、入口、上下游关系、身份权限、运行映射、历史尝试、未知与冲突，并绑定具体画像版本。

关联任务的知识继续遵守现有可见性与直接来源限制。引用旧知识不等于当前版本已覆盖，复用执行证据前应核对代码、环境、范围和前置条件。

## 10. 分阶段开发步骤

### 第 1 步：领域定义和完成契约（已完成）

**工作：**

- 定义评估轮次、代码目标、环境映射、画像事实、义务、尝试和完成结果。
- 固化必需覆盖、阻塞、失效、不适用和例外的含义。
- 建立程序完成判定契约，梳理所有现有结束路径。

**主要位置：** `db/tasks.go`、`db/schema.sql`、`server/engine.go`、`server/engine_timeout.go`，以及新增评估状态逻辑。

**验收：** 零资产、只有 fact、只有失败尝试、缺凭证或白盒队列仍运行，都不能被判为全覆盖完成。

### 第 2 步：任务创建与启动（已完成）

**工作：**

- 增加白盒模式、草稿、材料检查和显式启动。
- 新模式不依赖用户自定义结果目标，保留业务重点和操作约束。
- 页面和 Agent 创建流程统一；材料未就绪不启动发散 Planner。

**主要位置：** `db/tasks.go`、`server/server.go`、`server/orchestration.go`、`server/goals.go`、`server/task_codebases.go` 和创建任务界面。

**验收：** 无有效材料不能进入执行；草稿可恢复；两个创建入口行为一致；已有任务流程兼容。

### 第 3 步：代码清单和初始画像（已完成）

**工作：**

- 复用上传、版本、服务发现和语言适配器。
- 补齐自研模块、共享库、配置、部署对象的清点。
- 建立画像存储、证据引用和查询接口。
- 优先提取模块结构、入口、认证链、依赖和代码—部署映射。

**主要位置：** `server/codebase_discovery.go`、`server/code_audit_language*.go`、`server/java_code_db*.go`，新增画像持久化和提取逻辑。

**验收：** 能表达混合语言、共享库、多实例、配置冲突；推断不冒充运行事实；读取失败形成缺口。

### 第 4 步：覆盖义务生成、统一意图路由与评估 Planner 统筹

**工作：**

- 从第 3 步初始画像与代码清单由程序确定性生成本轮基础覆盖义务、前置依赖、幂等标识与验收规则。
- 扩展 `Intent` 负载与 `task_test_attempts`（携带 `execution_mode`、`obligation_id`、`round_id`、`attempt_id`、`profile_version`），不将旧证据边解释为执行依赖。
- 在 `server/engine.go` 恢复运行态 `AssessmentMode` 的 `Planner` 统筹，提供评估专用提示词、轮次级上下文切片查询工具与 `request_assessment_completion`，并严格落实三条程序硬护栏（Planner 不可删除必需义务、不可绕过证据验收、不可直接标 `done`）。
- 在 `Engine` 落地共享 `WorkerSlots` 并发软配额保护（当 `slots >= 2` 时 `code_audit_batch` 上限为 `slots - 1`，至少保留 1 槽位给动态与查码）；保留传统模式执行路径。

**主要位置：** `db/assessment.go`（及新增义务/尝试存储）、`db/exploration.go`、`agent/planner.go`、`agent/tools.go`、`agent/promptcatalog.go`、`server/engine.go`，新增义务生成与调度逻辑。

**验收：** 重复规划不重复派工；未满足依赖不能执行；`Planner` 能依据画像与缺口派发带 `execution_mode` 的意图；`Planner` 不能删除必需义务或直接标 `done`；`slots >= 2` 时批量白盒意图不会占满动态与查码槽位；意图完成但证据不足时义务不推进。

### 第 5 步：白盒执行器下沉（`code_audit_batch` / `code_investigate`）与 `MainAgent` 融合

**工作：**

- 将 `server/java_code_audit.go` 审计内核封装为 `Engine.runIntent` 在 `workCtx` 内直接调用的 `code_audit_batch` 执行器（支持非服务模块与共享库、注入轮次画像切片、保留 A/B/C 分级、真实读取校验、候选修复、补审和收尾扫描，并减少漏洞类型偏好示例）。
- 实现模块级 `Intent` + `code_audit_run_id` 检查点（`next_file_index` / `next_class_index`）断点续跑，以及**分片级增量落库与唤醒 `Planner`**（每完成一个分片即落库已读台账与候选并唤醒 `Planner` 并发调度动态测试）。
- 新增只读白盒 `agent.Worker` 执行模式 `code_investigate`（仅挂载只读代码/JavaCodeDB/画像/台账工具，严格无 Bash、无网络请求）。
- 将原 `whitebox_audit` 查询/优先级引导/确认后直投/`steer_work`/约束登记能力并入 `MainAgent`，评估模式前端任务详情隐藏独立「白盒审计 Agent」聊天入口，传统模式（`assessment_mode=false`）保留旧入口与手动审计兼容。
- 统一准入、暂停、恢复、取消、超时与删除排水控制，并以真实读取与补审台账验收代码审计义务。

**主要位置：** `server/engine.go`、`server/java_code_audit.go`、`server/code_audit_coverage.go`、`server/code_audit_control.go`、`server/task_code_audit_chat.go`、`db/code_audits.go`、`agent/worker.go`、`agent/mainagent.go`、`agent/promptcatalog.go`、任务详情会话界面。

**验收：** 不需逐服务手动启动；共享库与非服务模块进入审计；大模块每分片完成即可落库线索并唤醒 `Planner` 并发派发动态验证；暂停/取消/超时/重启后断点续跑不丢已审台账；`code_investigate` 严格无 Bash 与网络权限；评估模式通过 `MainAgent` 统一查看与操舵白盒进度；传统模式旧入口与手动审计不受破坏。

### 第 6 步：环境核实与动态测试（`dynamic_verify` 与双向反馈闭环）

**工作：**

- 建立环境映射、身份引用、结构化动态工作单和动态证据回填；强化 `dynamic_verify` 的只读代码切片查询能力。
- 贯通“白盒→动态”（基于静态候选与无候选入口覆盖生成运行测试）及“动态→白盒”（动态遇阻、鉴权/响应异常或部署冲突触发 `Planner` 派发 `code_investigate` 反向查码与更新画像）。
- 先贯通通用 HTTP 与已有环境执行能力，按实际需求扩展 RPC、消息和协议适配。

**主要位置：** `agent/worker.go`、`server/engine.go`、`traffic/`、已有 Finding/复测流程和新增动态尝试验收逻辑。

**验收：** 版本不一致时不错误复用证据；未复现不等于修复；无静态候选的入口也被测试；动态异常能触发定向白盒调查并更新画像。

### 第 7 步：增量事件、证据失效与原子收尾对账

**工作：**

- 通过 `task_assessment_events` 将分片新候选、新资产/新入口、知识修订和配置变化可靠送入 `Planner` 驱动增量重排。
- 支持证据失效（`stale`）、受影响义务重开、重复假设合并。
- 所有新模式结束路径（`request_assessment_completion`、心跳、超时收尾等）统一经过程序完成判定。
- 收尾对账使用轮次/计划版本条件原子提交，防止新工作与结束写入竞态。

**主要位置：** `agent/tools.go` 的目标操作、`agent/planner.go`、`server/engine.go`、`server/engine_timeout.go`、主任务状态写入、`db/assessment.go` 事件与评估轮次逻辑。

**验收：** 收尾时分片候选或动态新发现不会丢失；迟到结果不能推进新尝试；重启不丢缺口与检查点；没有活动意图不自动等于完成。

### 第 8 步：界面、兼容迁移与评估

**工作：**

- 前端统一展示评估阶段、画像、覆盖义务树、三类执行器进度（含 `code_audit_batch` 分片进度）、阻塞、证据和 Findings。
- 每个义务解释为什么需要测、已测什么、还缺什么。
- 核验评估模式单一 `MainAgent` 会话体验，并保证传统模式（`assessment_mode=false`）完整兼容，旧任务保留旧含义、不批量把历史 fact 转为新覆盖证据。
- 覆盖归档、恢复、任务关联、模型配置和源码发送确认兼容。
- 使用隔离夹具执行流程回归与真实模型质量评估。

**主要位置：** `web/src/app/(main)/function/tasks/`、`web/src/lib/types.ts`、`web/src/lib/api.ts`、任务归档/恢复及相关集成测试。

**验收：** 前端与程序完成条件一致；评估模式唯一交互入口与传统模式旧入口各司其职；老任务可读可运行；范围例外清晰可见；质量指标来自实际评估。

### 10.1 推荐首个可交付版本

先贯通：上传材料、初始画像、全部基础覆盖义务、自动白盒审计、部署入口动态测试、证据对账完成。

这个版本需要真实、可恢复、可解释。更深的架构提取和更多协议支持在这条路径稳定后增加。界面和兼容测试应随各步骤同步开发，不必全部推迟到最后。

## 11. 验证与评估

### 11.1 流程正确性

必须覆盖：

- 清单中存在但解析遗漏的文件不能静默消失。
- 自研共享库不是服务时仍进入审计。
- 不同部署配置不能无条件共享动态覆盖证据。
- 不同身份/租户的必要义务不能由一个普通请求替代。
- Agent 不能直接把任务改为全覆盖完成，也不能删除程序必需覆盖义务。
- 白盒与动态并行时暂停、恢复、取消和收尾一致。
- `code_audit_batch` 在暂停、取消、超时或服务重启后保留分片检查点，恢复时断点续跑且不重复计数。
- 多槽位（`slots >= 2`）下批量白盒扫描最多占用 `slots - 1`，不饿死动态验证与定向代码调查。
- `code_investigate` 严格保持只读权限，不能执行 Bash 或发起网络请求。
- 评估模式收敛为唯一 `MainAgent` 入口，传统模式（`assessment_mode=false`）原有白盒聊天与手动审计兼容不受影响。
- 代码、认证配置、部署映射变化触发相应失效。
- 旧任务知识可引用，但旧证据不自动计入本轮。
- 重复事件、执行重试和迟到结果不会重复登记或错误推进状态。

后端变更运行相关单测、隔离数据库集成测试及 `go test ./...`；前端运行 `npm run check`，涉及编译时运行 `npm run build:static`。不能使用正在运行的 ARTEX 业务数据库做测试。

### 11.2 漏洞发现质量

真实模型评估至少记录：

- 预期漏洞发现率和登记率。
- 安全对照误报。
- 重复候选和重复验证比例。
- 未读、未测、阻塞资产暴露情况。
- 无效探索与有价值延伸探索比例。
- 静态线索到有效动态证据的转化。

固定材料、环境、模型和提示词版本，保存原始输出和平台验收结果。A/B/C 分布与漏洞数量只作观察指标，不单独代表质量。本文没有提供或声称任何真实模型评估成绩。

## 12. 实施边界与成功标准

本方案实现的是有明确范围和证据的白盒驱动测试，不承诺全路径或全部漏洞可被自动发现。

成功标准是：用户提供有效材料和测试环境后，ARTEX 能建立可信的知识骨架，自动形成覆盖计划，执行静态和动态工作，解释每个对象的测试进度与缺口，并在统一、可审计的条件下完成本轮任务。

预算策略维持现状。类型开放、证据真实性、范围控制和历史兼容贯穿全部开发阶段。
